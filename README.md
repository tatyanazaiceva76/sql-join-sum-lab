# SQL: почему SUM после JOIN завышает итог

Небольшая лабораторная работа на Python и SQLite: найдите ошибку уровня детализации в отчёте и проверьте исправление на пограничных данных. Объяснение — на русском, данные полностью вымышленные.

## Что считаем

Метрика этой задачи: **сумма оплаченных заказов, у которых есть хотя бы одна позиция**. `orders.total_rub` — полная сумма одного заказа в целых рублях. Суммы отдельных позиций здесь не рассчитываются.

| Заказ | Статус | Сумма | Количество позиций |
|---|---|---:|---:|
| 1 | paid | 1000 | 2 |
| 2 | paid | 600 | 1 |
| 3 | cancelled | 900 | 1 |

Правильный итог — 1600. Если соединить заказы с позициями и затем выполнить `SUM(o.total_rub)`, получится 2600: первый заказ окажется в двух строках.

`SUM(DISTINCT o.total_rub)` случайно исправляет исходный пример, но ломается, когда два разных заказа имеют одинаковую стоимость. DISTINCT устраняет одинаковые **числа**, а не повторные появления одного заказа.

Нужна только проверка наличия позиции, поэтому сохраняем по одной строке на заказ:

```sql
SELECT COALESCE(SUM(o.total_rub), 0)
FROM orders AS o
WHERE o.status = 'paid'
  AND EXISTS (
    SELECT 1 FROM items AS i
    WHERE i.order_id = o.order_id
  );
```

Ноль вместо NULL для пустого результата — явно выбранное условие этой метрики, а не универсальное правило отчётности.

## Шесть сценариев

Вывод: имя сценария и результаты трёх запросов в порядке `JOIN`, `DISTINCT`, `EXISTS`.

```text
base (2600, 1600, 1600)
same_price (3600, 1600, 2600)
no_items (2600, 1600, 1600)
more_lines (3600, 1600, 1600)
no_paid (None, None, 0)
empty (None, None, 0)
```

- `same_price`: добавляем другой оплаченный заказ на 1000 рублей с позицией.
- `no_items`: добавляем оплаченный заказ без позиций — по условию задачи он не учитывается.
- `more_lines`: добавляем позицию, не меняя сумму заказа.
- `no_paid`: все заказы отменены.
- `empty`: обе таблицы пустые.

Тесты сравнивают исправленный SQL с независимым расчётом по идентификаторам заказов в Python и проверяют, что известные неправильные варианты действительно обнаруживаются. Чтобы исследовать другой случай, измените учебные данные в копии скрипта и сначала сформулируйте ожидаемый результат.

## Границы примера

Это упражнение о кардинальности соединения, не готовая система финансового учёта. Возвраты, скидки, разные валюты, NULL в исходных суммах и история статусов не моделируются. Производительность запросов не измерялась. Не заменяйте все JOIN на EXISTS: выбор зависит от задачи.

Если нашли ошибку, можно открыть Issue с минимальным **вымышленным** набором данных. Не публикуйте реальные заказы, персональные данные, ключи или пароли.
