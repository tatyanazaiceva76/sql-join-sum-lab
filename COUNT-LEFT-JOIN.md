# Почему LEFT JOIN показывает одну продажу вместо нуля

В отчёте должны оставаться **все товары каталога**, даже если у них нет ни одной
оплаченной записи. `LEFT JOIN` уже поставили, а у пустого товара получается 1.
При добавлении фильтра статуса товар вообще исчезает. Разберём обе ошибки на
одном маленьком примере.

Это бесплатная самостоятельная лаборатория. Покупать книгу, регистрироваться
или отправлять свои данные не нужно. Все записи вымышленные; код работает
только с временной SQLite-базой `:memory:`, без сети и сторонних пакетов.

## Сначала зафиксируйте метрику

Одна строка результата — **один SKU из products**. Значение — число строк
`sales` этого SKU со статусом `paid`. Мы не считаем количество проданных штук,
уникальных заказов или выручку: в этой учебной схеме таких полей нет.

В каталоге есть A (блокнот), B (папка), C (альбом). У A две оплаченные записи,
у B нет записей, у C одна отменённая. Правильный результат: **A = 2, B = 0, C = 0**.
Ключ SKU уникален. `sale_id` — непустой идентификатор существующей строки
`sales`; поле `comment` может содержать NULL.

## Ошибка 1: посчитали сохранённую строку товара

```sql
SELECT p.sku, COUNT(*) AS paid_rows
FROM products AS p
LEFT JOIN sales AS s ON s.sku = p.sku AND s.status = 'paid'
GROUP BY p.sku
ORDER BY p.sku;
```

Получится A = 2, B = 1, C = 1. Для B и C соединение сохранило по строке
каталога с NULL на стороне `sales`. Звёздочка считает эти строки тоже.
Название столбца `paid_rows` не делает подсчёт правильным.

## Исправление: считать совпавший непустой ключ

```sql
SELECT p.sku, COUNT(s.sale_id) AS paid_rows
FROM products AS p
LEFT JOIN sales AS s ON s.sku = p.sku AND s.status = 'paid'
GROUP BY p.sku
ORDER BY p.sku;
```

Теперь A = 2, B = 0, C = 0. У совпавших записей `sale_id` заполнен; у сохранённой
строки без совпадения он NULL. Не подставляйте сюда любое правое поле:
`COUNT(s.comment)` пропустит настоящую оплаченную запись с комментарием NULL.
Пустая строка `''` — другое значение: её `COUNT(s.comment)` учитывает.

## Ошибка 2: условие переехало в WHERE

Если соединять только по SKU, а `s.status = 'paid'` перенести в `WHERE`,
получится только A = 2. Нулевые товары исчезнут: фильтр отбросит и сохранённую
строку B с NULL, и отменённую запись C.

Попытка дописать `OR s.sale_id IS NULL` вернёт B, **но не C**. Для C совпадение
по SKU уже было — отменённая запись. Поэтому отдельной строки с NULL ему не
создали. После фильтрации он исчезнет. В этой задаче ограничиваем совпадения
статусом в `ON`, сохраняя весь каталог слева.

Это не правило «всегда переносить WHERE в ON». Если задача — показать только
товары с покупками, требование к составу результата другое.

## Запуск и проверка своих предположений

Скачайте рядом `sql_count_lab.py`, `test_sql_count_lab.py` и этот файл
`COUNT-LEFT-JOIN.md` (он нужен для проверки примеров из объяснения).
Нужен Python 3 со стандартным модулем sqlite3.

```sh
python3 sql_count_lab.py
python3 -m unittest -v test_sql_count_lab.py
```

Если команда Python у вас называется `python` или `py`, замените только
`python3`. SQL-таблицы и исходные данные находятся в `SCHEMA` внутри скрипта.
Изменения сценариев применяются только к отдельной базе в памяти. Не вставляйте
в неё SQL из неизвестных источников и не подключайте рабочую базу.

```text
base [('A', 2), ('B', 0), ('C', 0)]
empty_sales [('A', 0), ('B', 0), ('C', 0)]
no_paid [('A', 0), ('B', 0), ('C', 0)]
new_paid [('A', 2), ('B', 0), ('C', 1)]
unpaid_only [('A', 2), ('B', 0), ('C', 0)]
same_name [('A', 2), ('B', 0), ('C', 0)]
empty_catalog []
```

Перед запуском попробуйте объяснить последние три строки:

1. У B появилась запись `new`. Почему счётчик всё ещё ноль?
2. У всех товаров стало одинаковое название. Почему в ответе три SKU?
3. Удалён весь каталог и записи продаж. Почему результат пустой, а не одна строка с нулём?

Ответы: учитываются только `paid`; группировка идёт по уникальному SKU, не
названию; нет товаров, для которых нужно создать строку отчёта. Это результат
группировки пустого каталога, а не одиночный `COUNT(*)` без `GROUP BY`.

Тесты сверяют SQL с независимым построчным подсчётом на Python, проверяют
ограничения ключей и показывают контрпримеры четырём неправильным запросам.
Успешный тест не означает, что запрос подходит любой реальной схеме:
дополнительное соединение один-ко-многим может снова размножить записи.
